# 視覺回歸驗收：怎麼證明「畫面沒變」

適用節點 6～10，在「畫面樣式不得改變」是驗收條件時是必做項（見 SKILL.md 的「硬約束」一節）。

這一章要解決的問題是：**框架換代造成的差異，多數不是「某個 class 壞掉」，而是「整頁往下移了 2px」或「某個欄位比容器寬 30px」。** 這兩種靠 grep 抓不到、靠肉眼比截圖也抓不到，只有量測抓得到。

## 先建立一份可以並排比對的「升級前」

**不要用「先存一批基準截圖、改完再跟存檔比」的做法。** 存檔基準隔一段時間再比，字型快取、瀏覽器版本、系統縮放任何一項不同，都會製造出一堆與改動無關的假差異，而你會花時間去追它們。

正確做法是**同時跑兩台伺服器**，同一個瀏覽器、同一次執行、同一組等待條件下拍兩張圖：

```bash
# 升級前那份用 git 匯出，不要動工作區（git worktree 在部分環境會失敗，archive 比較穩）
mkdir -p /tmp/orig && git archive HEAD | tar -x -C /tmp/orig
(cd /tmp/orig && python -m http.server 8900) &
python -m http.server 8899 &          # 工作區＝升級後
```

這也是為什麼**每個節點都要獨立 commit**（SKILL.md 已列為原則）：有乾淨的 HEAD 才有得比。

### 如果舊站現在還在線上跑，優先拿正式站當基準

上面「同時跑兩台伺服器」的做法假設「升級前」只存在於 git 歷史裡。但如果這次要對齊的目標站現在仍然掛在正式環境（例如接手一個還在服務的舊站、要求「改完要跟線上一致」），**直接抓正式站的 CSS／JS／HTML 原始碼逐字比對，比本地 `git archive` 快照更可靠**——本地快照只包含版控收進去的檔案，漏得到「正式站上有、但沒被特別注意到、也可能根本沒進版控」的客製檔案（`04-bootstrap-upgrade.md` 提到的 `bootstrap-theme.css` 就是一例）。有正式站可以直接比對時，把它當第一基準；`git archive` 留給「正式站已經下線、只剩歷史紀錄」的情況。

實務上用 `curl` 把正式站的樣式表、腳本抓下來對照最快：

```bash
curl -s -m 20 "http://example.com/css/style.css" -o style-live.css
```

**這台機器的 WebFetch 工具會把 `http://` 網址自動升級成 `https://` 再連線**，如果目標站的 SSL 憑證跟它自己的 hostname 對不上（常見於用共用 IP、CDN、或年久失修沒續約憑證的舊站），WebFetch 會直接回報「Hostname/IP does not match certificate's altnames」而失敗，即使你給的是純 `http://` 網址。這不代表網站連不上，退回用 `curl`（不做 https 升級、不驗證憑證鏈）就能正常抓到原始碼。判斷方法：WebFetch 報憑證錯誤時，先用 `curl -sI <http網址>` 確認網站本身有沒有回應，再決定要不要整段改用 `curl`。

## 三層驗收，照這個順序看

| 層 | 看什麼 | 抓得到什麼 | 抓不到什麼 |
|---|---|---|---|
| 1. 靜態掃描 | 舊寫法有沒有殘留 | 漏改的 class、屬性 | 「少寫了一個 class」、結構性行為變化 |
| 2. 幾何不變量 | 頁面總高、水平溢出量 | 版面崩掉、元素溢出容器 | 顏色、字級 |
| 3. 逐屬性與逐像素 | computed style、畫面 | 其餘所有差異 | 內容不確定性造成的假差異 |

第 2 層最便宜也最有診斷價值，卻最常被跳過。兩個指令就有：

```js
// 頁面總高：改動前後應該完全相同
document.documentElement.scrollHeight
// 水平溢出量：大於 0 代表有東西比容器寬
document.documentElement.scrollWidth - document.documentElement.clientWidth
```

**只要總高或溢出量對不上，就是版面真的變了，先追那個，不要先看像素數。** 像素差異是結果，這兩個數字比較接近原因。

本 skill 附的兩支腳本分別對應第 3 層的兩半：

- `scripts/dump-computed-style.py` — 逐屬性比對，回答「變的是哪一個屬性、從什麼變成什麼」
- `scripts/compare-screenshots.py` — 逐像素比對，回答「哪一塊、多大範圍變了」，並一併回報第 2 層的兩個不變量

兩者缺一不可：只做像素比對會卡在「知道不對但不知道改哪裡」；只做屬性比對會漏掉版面位移這種不歸屬於單一元素的變化。

## 量測本身的五個陷阱

這五項全都會製造假差異或掩蓋真差異，而且都不會有錯誤訊息。

1. **不要用整頁截圖（`full_page=True`）比對。** 整頁擷取會臨時改變視窗尺寸重新繪製，實測會出現「圖示字型的 glyph 整個沒畫出來」這種只在其中一邊發生的現象，看起來就像某個按鈕消失了。改用視窗截圖 + 逐段捲動。判斷方法：同一個位置用元素截圖或視窗截圖再拍一次，差異歸零就是擷取假象。
2. **等 `document.fonts.ready`。** 圖示字型晚一步就緒，glyph 不會畫出來，但元素的尺寸與 computed style 全都正常——所以你會看到「所有樣式都一樣但圖示不見了」這種矛盾結果。
3. **凍結輪播與動畫。** 目前張數每次載入都不同。Swiper 可以用 `el.swiper.autoplay.stop()` 加 `slideTo(0, 0)`，其他套件要各自處理。沒凍結的話，差異清單會被輪播內容淹掉，真正的問題找不到。
4. **傾印的屬性清單一定要含 `width`／`height`。** 只比對顏色與字級時，「某個欄位比容器寬 30px」這種問題完全不會出現在清單裡。這是實際踩過的漏網——溢出是靠第 2 層的不變量才抓到的。
5. **元素的可見性會影響量測。** 瀏覽器對沒有排版的元素（`display:none`、還沒輪到的輪播張數）回傳的是指定值而不是使用值，例如 `margin` 會回 `auto` 而不是實際像素。比對時要一併記錄可見性，前後可見性不同的元素直接排除，否則會產生一批看起來很嚇人、其實不存在的差異。

## 判讀差異的順序

拿到差異清單之後，照這個順序處理，可以少走很多冤枉路：

1. **先重跑一次。** 同樣條件重跑，數字如果會變，那個差異就是內容不確定性（輪播、隨機排序、JS 動畫時序），不是版面問題。實測有頁面在兩次相同執行之間從 5662px 跳到 36394px——追它是白費力氣。
2. **差異數量大時，先找單一全域值。** 整張圖幾乎全紅通常不是幾百處都壞了，而是有一個全域值沒調回來（字級、行高、gutter、容器寬度）把整頁的東西往下或往旁邊推。先找那一個，不要一塊一塊修。
3. **同一個 bbox 出現在多支頁面 = 共用元件。** header／footer 抽成共用區之後（節點 3），一個差異會在每支頁面重複出現。改一次全部消失，所以先處理它，剩下的清單會短很多。
4. **量到的位移要往上追一層。** 「某個元素的百分比外距差了 0.9px」不是問題本身，是它的父層寬度差了 30px 的症狀。直接量父層鏈的寬度，比在子元素上調數字有效。
5. **剩下的每一處都要說得出原因。** 說不出原因就代表還沒查完。可接受的結論有三種：這是使用者核准的變更、這是量測假象（附上用另一種量法驗證的結果）、這是已知且使用者接受的取捨。「有些微差異」不算結論。

## 掃描指令要先自我驗證

**回報 0 筆的掃描指令，可能是指令本身壞了。** 這次實際踩到：一道用來檢查「SCSS 有沒有鎖定 `col-*` class」的 grep 回報 0 筆，於是判定「改 grid class 名稱不會影響專案樣式」——實際上有 22 條。指令是正則語法在該環境下不成立，grep 沒有報錯、只是安靜地不匹配。

養成兩個習慣：

- **凡是用來證明「沒有問題」的掃描，先拿一個已知會命中的字串跑一次**，確認指令真的抓得到東西，再相信它回報的 0。
- **複雜的長正則（多個 `|` 分支、`\b` 邊界、跳脫字元）在不同 grep 實作下的行為不一樣**，拆成幾道簡單指令比湊一道漂亮的可靠。

同一類的紀律還有一條：**不要把推測寫進程式碼註解。** 這次寫過「站台有一條 `.sticky-header .container { width: 100% }` 所以要用 width 而不是 max-width」——那條規則根本不存在，真正的原因是層疊位置。註解裡的錯誤結論會被下一個人當成查證過的事實。要寫原因就先查證，查不到就寫「原因未確認」。

這條紀律不只適用靜態掃描，**用 Playwright 之類的工具做互動測試時，斷言本身也要先確認有沒有辨識力。** 這次實際踩過的例子：改寫一個下拉選單的展開／收合邏輯之後，寫了一個斷言「滑鼠移到選單上，子選單 `is_visible()` 應為 `True`」，測試通過，但**這個斷言在「CSS 正確運作」和「CSS 完全沒生效、選單本來就永遠展開」兩種情況下，印出來的結果一模一樣**——因為兩種情況下子選單都是可見的，差別只在於「可見」是不是真的由 hover 這個動作造成的。真正有辨識力的斷言要包含一個**反例基準值**：先確認滑鼠不在選單上時子選單是隱藏的（`is_visible()` 應為 `False`），再確認 hover 之後變成可見，這樣測試才能區分「功能正常」跟「功能整個沒生效、只是剛好一直顯示」。同樣的道理也適用於任何「移除某個動作後，某狀態應該消失」的行為（例如選單收合、彈窗關閉）——只驗證「觸發後出現」，不驗證「移除觸發後消失」，會漏掉狀態卡住不會收合的 bug。
