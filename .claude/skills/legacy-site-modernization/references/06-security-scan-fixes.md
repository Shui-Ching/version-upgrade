# 節點 10 專章：修復弱點掃描與原始碼掃描的發現項

**前提：節點 7（BS5 升級）、8（移除 jQuery）、9（第三方套件升級）要先做完。** 舊站的掃描報告裡，「相依套件有已知漏洞」類的發現項通常佔一半以上，而它們會被套件升級**整批消掉**。順序反過來的話，你會花時間逐項處理一批即將被升級動作解決的發現項，而且升完之後分不清剩下的發現項是原本就有、還是升級新帶進來的。

同時：這個節點多半跟「畫面樣式不得改變」的硬約束綁在一起（見 SKILL.md 的「硬約束」一節），因為版更的來由本來就是資安檢測。每一個修法動手前都要先想「這會不會動到畫面」。

## 兩種掃描的差異，以及為什麼要分開處理

台灣的公部門與企業案子通常會同時要求這兩種，但它們看的東西不一樣、修法也不一樣：

| | 弱點掃描（VA／DAST） | 原始碼掃描（SAST） |
|---|---|---|
| 掃什麼 | **跑起來的網站**：實際發出 HTTP 請求，看回應標頭、cookie、可存取的路徑、載入的套件版本 | **原始碼檔案**：靜態分析語法，找危險函式呼叫與資料流 |
| 常見工具 | Nessus、Acunetix、OWASP ZAP、Burp | Fortify、Checkmarx、SonarQube、Semgrep |
| 典型發現項 | 缺少安全標頭、cookie 沒有 `Secure`／`HttpOnly`、套件版本有 CVE、目錄可列表、TLS 設定弱 | `innerHTML` 的 XSS 資料流、寫死的密碼、不安全的隨機數、路徑穿越 |
| **修在哪裡** | **一大半修在伺服器設定，不是前端程式碼**（`.htaccess`、Nginx conf、主機設定） | 幾乎都修在程式碼裡 |
| 誤報率 | 中（版本判定常常抓錯） | 高（靜態分析追不出實際的資料流限制） |

**最重要的一件事：弱點掃描的發現項有相當比例不是你改 HTML／JS 能解決的。** 缺少 `Content-Security-Policy`、`X-Frame-Options`、`Strict-Transport-Security` 這類標頭，要在 web 伺服器層設定；純靜態站可以用 `.htaccess`（Apache）或請主機管理者改 Nginx 設定。**動手之前先確認你有沒有這個權限、主機是什麼**——如果沒有，這些項目要整理成一份「需要主機端配合」的清單交出去，而不是在前端硬湊（例如用 `<meta http-equiv>` 模擬部分標頭，效力與涵蓋範圍都不同，只能當退路且要註明）。

## 步驟 1：把報告整理成可執行的清單

拿到報告先不要從第一項開始修。掃描報告的排序通常是照風險等級或掃描順序，不是照修復難度，照著順序修會在幾個困難項目上卡住。

先把每一項標上三個維度：

1. **修在哪一層**：前端程式碼／伺服器設定／第三方套件版本／設計問題（需要功能調整）。
2. **會不會動到畫面**：不會／可能會／一定會。「一定會」的項目要單獨列出來先問使用者。
3. **是不是誤報**：確定是／確定不是／待查。

然後照這個順序做，理由是「先把便宜又安全的做掉，把清單縮短，剩下的才是真正要討論的」：

1. **套件版本類**（節點 9 應該已處理，這裡只確認報告上的版本號跟現況一致）。
2. **伺服器設定類**（集中在一兩個設定檔，一次改完，完全不動畫面）。
3. **前端程式碼類、不動畫面的**（`rel="noopener"`、SRI、移除 console 輸出）。
4. **前端程式碼類、會動畫面的**（要先問使用者）。
5. **誤報**（整理說明，見步驟 3）。

清單本身就是交付物的一部分——最後要能對著原始報告逐項說明「這項怎麼處理的」，沒有任何一項是空白的。

## 步驟 2：常見發現項與修法

### 2-1 相依套件有已知漏洞（CVE）

舊站最常見的一批，也是最容易解決的一批。

```bash
# 有 npm 的話（節點 5 導入過建置工具）
npm audit
# 沒有 npm 的話，把 HTML 裡所有 CDN 與本地套件的版本號列出來，逐一查 CVE
grep -rEon '(cdn\.jsdelivr\.net|cdnjs\.cloudflare\.com|unpkg\.com)[^"'"'"']*' --include='*.html' .
grep -rn 'Bootstrap v\|jQuery v\|@version' --include='*.js' --include='*.css' . | head -30
```

修法就是升到修掉該 CVE 的版本，也就是節點 9 做的事。三個要注意的地方：

- **升級後要同步更新 SRI 雜湊**（節點 6 的流程），漏掉的話資源會被瀏覽器安靜拒絕，畫面直接壞掉。
- **掃描器判定版本的方式常常是看檔名或檔案內的版本註解**，所以就算你升級了、但檔名還留著舊版號（`js/jquery-2.0.0.min.js` 裡面放的其實是新版），複掃還是會報。檔名要一起改。
- **`_deprecated/` 之類的暫存資料夾如果會被部署出去，裡面的舊套件一樣會被掃到**。這是很常見的「明明升級了還是被報」的原因。部署前確認這些資料夾沒有上傳，或直接在這個節點清掉。

### 2-2 缺少 HTTP 安全標頭

弱掃必報的一類，修在伺服器設定。純靜態站用 Apache 的話是 `.htaccess`：

| 標頭 | 作用 | 會不會影響畫面 |
|---|---|---|
| `X-Content-Type-Options: nosniff` | 禁止瀏覽器猜測 MIME 型別 | 不會 |
| `X-Frame-Options: SAMEORIGIN` | 防止被嵌進別人的 iframe（點擊劫持） | 不會，除非站台本來就要被別站嵌入 |
| `Referrer-Policy: strict-origin-when-cross-origin` | 限制送出的 referrer 資訊 | 不會 |
| `Strict-Transport-Security` | 強制 HTTPS | **要先確認站台全站都能走 HTTPS**，否則會鎖死 |
| `Content-Security-Policy` | 限制可載入的資源來源 | **最容易把站弄壞的一個**，見下方 |
| `Permissions-Policy` | 關閉不需要的瀏覽器功能（相機、麥克風等） | 不會 |

**CSP 要特別小心**：它會擋掉所有不在白名單裡的資源，而舊站幾乎一定有你沒盤點到的外部資源（Google Analytics、Facebook SDK、字型、地圖嵌入）。做法是**先用 `Content-Security-Policy-Report-Only` 模式跑一輪**，收集瀏覽器回報的違規清單，把該放行的加進白名單，確認乾淨之後才改成正式的 `Content-Security-Policy`。直接上正式模式的結果是頁面上一堆東西不見了，而且違規訊息只出現在 console，不會有任何畫面提示。

另外，如果節點 5 的「inline JS／CSS 一律搬出 HTML」有確實做到，CSP 才有可能不需要 `'unsafe-inline'`——這是那條規則除了可維護性之外的資安價值，可以在報告裡點出來。

### 2-3 XSS：`innerHTML` 與 DOM sink

原碼掃描最常報的一類。掃描器會標出所有寫入 `innerHTML`、`outerHTML`、`document.write`、`eval`、`insertAdjacentHTML` 的位置。

```bash
grep -rEon 'innerHTML|outerHTML|document\.write|insertAdjacentHTML|\<eval\(|new Function\(' --include='*.js' --include='*.html' .
```

逐處判斷寫入的字串來源（判準與改法見 `05-remove-jquery.md` 的陷阱 8）：寫死的樣板字串可以留；只要有任何來自網址參數、表單輸入、後端回傳資料的變數，就要改成 `textContent`，或用 `document.createElement()` 逐個建立元素、文字部分用 `textContent` 設定。

**這個節點跟節點 8 有重疊**：移除 jQuery 時把 `.html()` 改寫成原生的那一輪，就應該一併處理掉。如果那時候處理過了，這裡只是確認掃描報告上的位置都已經涵蓋。

`node 3` 的共用區注入（`include.js` 用 `outerHTML` 塞 header/footer）會被掃描器報出來，但來源是專案自己的靜態檔案、不含使用者輸入——這是典型的誤報，照步驟 3 處理。

### 2-4 缺少 SRI／外部資源完整性

節點 6 已經定下規則：CDN 資源要有 `integrity` 且必須與 `crossorigin="anonymous"` 成對出現。這裡是驗收：

```bash
# 抓出沒有 integrity 的外部 script／link
grep -rEon '<(script|link)[^>]*(https?:)?//[^>]*>' --include='*.html' . | grep -v 'integrity='
# 抓出有 integrity 卻沒有 crossorigin 的（這種會直接把資源弄壞）
grep -rEon '<(script|link)[^>]*integrity=[^>]*>' --include='*.html' . | grep -v 'crossorigin='
```

第二個指令的命中是**比沒有 SRI 更嚴重的問題**：資源會被瀏覽器拒絕套用、畫面壞掉，而且錯誤訊息不會指向 `crossorigin`。

### 2-5 `target="_blank"` 缺少 `rel`（反向 tabnabbing）

節點 4 做過一輪，這裡驗收：

```bash
grep -rEon '<a[[:space:]][^>]*>' --include='*.html' . | grep '_blank' | grep -v 'rel='
```

用 `-o` 逐標籤切出來再過濾，不要整行比對——理由見 SKILL.md 的「掃描指令的寫法」。修法與例外情況見 `03-a-to-button.md`。

### 2-6 敏感資訊寫死在前端

原碼掃描會找寫死的 API 金鑰、密碼、連線字串。舊站常見的是留在註解裡的測試帳密、後台網址、以及第三方服務的金鑰。

```bash
grep -rEin '(api[_-]?key|secret|password|passwd|pwd|token|access[_-]?key)[[:space:]]*[:=]' --include='*.js' --include='*.html' --include='*.json' .
```

**注意：把金鑰從程式碼裡刪掉，不等於它安全了。** 只要這份程式碼進過版本控制或曾經上線，那把金鑰就必須視為已外洩，要去對應的服務後台**作廢並重新產生**。這一點一定要在報告裡明講，因為使用者很容易以為刪掉就沒事了。

前端本來就藏不住秘密（任何寫在 JS 裡的東西使用者都看得到）。如果站上真的需要呼叫需要金鑰的服務，正解是後端代理；純靜態站沒有後端的話，這件事要升級成架構層級的討論，不是這個節點能解決的，列出來交給使用者決定。

### 2-7 Cookie 屬性、目錄列表、其他伺服器層項目

- **Cookie 缺少 `Secure`／`HttpOnly`／`SameSite`**：純靜態站自己通常不設 cookie，命中多半來自第三方追蹤碼（GA、FB Pixel）——那些 cookie 不是你設的、也改不了屬性，屬於誤報或「需第三方配合」，照步驟 3 說明。若站上真有自己用 JS 設的 cookie，`HttpOnly` 依定義做不到（JS 設的 cookie 就是要給 JS 讀），要改成後端設定才有辦法，同樣是架構層級的討論。
- **目錄可列表（Directory Listing）**：伺服器設定，Apache 用 `Options -Indexes`。
- **備份檔／原始檔可下載**（`.bak`、`.zip`、`.git/`、`package.json`、`scss/` 原始碼）：部署時不該上傳的東西被上傳了。修法是整理部署清單，或用 `.htaccess` 擋掉。**這一項在節點 5 導入 npm + sass 之後特別容易中招**——`node_modules/`、`scss/`、`package.json` 都不該部署出去。
- **TLS／憑證設定**：主機端的事，整理成清單交出去。

## 步驟 3：誤報怎麼處理

掃描報告的誤報率不低，尤其原碼掃描。**誤報不是「不用管」，是「要寫說明」**——驗收方要的是每一項都有交代，沒有交代的項目會被當成未處理。

每一個判定為誤報的項目，說明要包含三件事：

1. **掃描器報什麼**（原文的規則名稱與位置）。
2. **為什麼在這個情境下不成立**：具體指出資料來源。例如「這裡的 `outerHTML` 寫入的是專案內的靜態檔案 `components/header.html`，內容不含任何使用者輸入或外部資料」，而不是「已確認安全」。
3. **什麼情況下會變成真的漏洞**：例如「若日後 `components/` 底下的檔案改為由後端動態產生，這裡就需要改寫」。這一句是給未來維護者的，也讓驗收方看得出你真的分析過而不是隨手標誤報。

**判不出來就不要標誤報。** 標成誤報等於為它背書；不確定的項目照真的漏洞處理（改掉），或列進「待確認」交給使用者，成本比誤判低得多。

## 步驟 4：複掃與交付

### 4-1 修完先自己驗一遍再送複掃

送複掃之前，能自己驗的先驗：

- 前端程式碼類：用步驟 2 各節的 grep 指令再跑一次，確認歸零。
- 伺服器標頭類：`curl -I https://<站台網址>` 看回應標頭，確認設定真的生效了。**`.htaccess` 寫了不等於生效**——主機可能沒開 `AllowOverride`、也可能 `mod_headers` 沒載入，這種情況下設定檔靜靜地被忽略。
- CSP：開瀏覽器 console 看有沒有違規訊息。

### 4-2 畫面沒變的證明

如果這次的硬約束是「畫面樣式不能改變」，複掃通過只是一半的驗收。另一半是像素比對的結果，做法見 `04-bootstrap-upgrade.md` 的「5-3 像素比對」。這個節點的修改多數不動畫面，但有幾個例外要特別回頭看：

- CSP 上線後，被擋掉的資源會讓畫面少東西（字型沒載到、地圖空白）。
- 移除的第三方追蹤碼或外掛可能同時帶著樣式。
- 改寫 `innerHTML` 為 `createElement` 時，如果原本的字串裡帶著 class，重建時漏掉就會掉樣式。

### 4-3 交付文件

對著原始掃描報告逐項列出處理結果，一項都不能空白。每一項至少寫：

| 欄位 | 內容 |
|---|---|
| 報告編號／項目名稱 | 照掃描報告的原文，方便驗收方對照 |
| 風險等級 | 照報告 |
| 處理結果 | 已修復／誤報（附說明）／需主機端配合／需使用者決策（附選項） |
| 修改位置 | 檔案路徑與行號，或設定檔位置 |
| 驗證方式 | 怎麼確認修好了（grep 指令、`curl -I` 的輸出、複掃結果） |

**「需主機端配合」與「需使用者決策」不是失敗，是正確的分類**——把改不到的東西硬說成已修復，複掃會直接打臉。這兩類要寫清楚卡在哪、需要誰做什麼，讓使用者拿著就能去推動。
