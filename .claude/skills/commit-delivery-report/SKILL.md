# 工作項目 × Commit 對照表

最後更新：2026-08-19（權威版本在 [github.com/Shui-Ching/version-upgrade](https://github.com/Shui-Ching/version-upgrade)）

## 這份文件是什麼

一份交付文件，回答兩個問題：

1. **對客戶／PM**：你驗收清單上的每一項，做完了沒？由哪些 commit 完成？
2. **對接手工程師**：這些改動我要配合做什麼，不做會怎樣？

它不是 CHANGELOG。CHANGELOG 是「改了什麼」，這份是「**你要跟著做什麼**」。
每一列的重點都在第三欄。

## 核心原則：骨架是驗收清單，不是 git log

最常見的錯誤是照 commit 時序排版，然後每筆寫一句摘要。那是 `git log --oneline`
的分行版，客戶看不出「我要的 12 項做完了幾項」。

正確做法反過來：

1. **先取得工作項目清單**——客戶的需求單、弱掃報告、驗收清單、報價單項目。
   沒有的話先向使用者要，不要自己從 commit 反推分類。
2. 把每一筆 commit **歸類**到某個工作項目底下。
3. 歸不進去的，一律收進「未歸屬於上述 Task 的 commit」章節。

第 3 步不可省略。它是這份文件的完整性保證：**任何一筆 commit 都不能消失**。
整理完務必核對 commit 總數與已列出的筆數是否相符。

## 文件結構

```
標題：<專案> 工作項目 × Commit 對照表
引言：分支 ｜ 整理日期 ｜ 進度 N／N 完成

## 總覽              ← 一張表看完全部，這是客戶唯一會細看的部分
## 1. <工作項目>      ← 每項一節，順序照驗收清單，不照時間
## 2. <工作項目>
...
## 未歸屬於上述 Task 的 commit
## 交付清單（工程端一次看完）
```

### 總覽表

| # | Task | 狀態 | Commit 數 | 工程端須配合 |

- Task 名稱**照抄驗收清單的原文**，不要改寫成你的用語，客戶要能逐字對得起來。
- 狀態用 ✅ 完成／🚧 進行中／⛔ 未處理，不要只寫百分比。
- 「工程端須配合」在總覽裡濃縮成一句，細節留給各節。
- **「Commit 數」的計數規則要一致**：建議算「本次批次的 commit」，
  不含標「（前置）」的鋪路 commit，也不含跨 Task 借列的。
  規則自己定沒關係，但十幾個 Task 要用同一套，否則客戶逐節點數會對不起來。

### 各節的表格

固定三欄：

| Commit | 內容 | 工程端須配合 |

- **Commit** 用 7 碼短 hash，加反引號。
- **內容**寫「做了什麼、影響範圍多大」。有數量就寫數量（「17 頁共 168 處」
  比「加上 lazy loading」有說服力，也讓工程端估得出自己那邊的工作量）。
  順手寫下非直覺的決策理由（「各頁前 3 張保留不加，避免影響 LCP」）。
- **工程端須配合**沒有就寫 `—`，不要留空白。

節內 commit 多時再切子表（`### 主要 commit 批次`／`### 後續補丁`／
`### 升級後跑版修正`），不要一張三十列的長表。

## ⚠️ 的判準

⚠️ 是這份文件最有價值的東西，浮濫使用就失效了。只給**不照做就會出事**的項目：

| 情況 | 標不標 |
|---|---|
| 事件綁定 selector 變了，不改就沒反應 | ⚠️ |
| 新增的字型檔漏傳，圖示全部消失 | ⚠️ |
| `<head>` 在後端模板，切版稿改不到，工程端不改就沒生效 | ⚠️ |
| 按鈕未綁動作，等後端接 | ⚠️ |
| 只是「需部署 CSS／js」 | 不標 |
| 只是「部署時一併移除舊目錄」 | 不標 |

判準一句話：**漏掉會壞掉的標 ⚠️，漏掉只是沒更新的不標。**

### 切版稿特有的高風險：外觀正常，功能壞掉

切版專案有一類改動特別危險——`<a>`／`<span>` 改成 `<button>`、
class 名稱調整、DOM 層級變動。因為 CSS 通常採「新舊選擇器並列」而非取代，
**畫面上完全看不出問題，壞掉的只有 JS 綁定**，而切版稿沒有真實資料流，
在切版稿上測不出來。

凡是這類改動，在該節結尾加一段引言區塊點明原因，並要求逐條檢查標 ⚠️ 的項目。
只在表格裡寫「事件綁定要改」，工程端很容易因為「我打開看起來好好的」而跳過。

## 幾個容易處理錯的情況

**一筆 commit 跨多個 Task**：兩節都列，並在其中一節加註
「`<短 hash>` 同時列在 Task 2」。不要為了「乾淨」只列一次——客戶是逐項驗收的，
少列會讓那個 Task 看起來沒做完。

**這個階段之前的鋪路 commit**：內容欄前面加「（前置）」。
它們算數，但要讓人看出不屬於本次批次。

**純版號破快取的 commit**：不要逐筆列表格。摺疊成一行短 hash 並列，
標題寫「版本號破快取（工程師可略）」。判準是**只有 query string 改動**——
只要夾帶任何實質內容變更，就不能標可略，要照常列。

**commit 訊息自帶「(工程師可略)」——不等於對照表可以省略**：
這兩個「可略」的受眾不同。commit 訊息上的是說「工程師不必看這筆 diff」；
對照表要回答的是「這個驗收項目做了沒」。實務上自帶標記的 commit 裡，
往往只有純版號那幾筆能摺疊，其餘（移除死檔、加 lazy loading、套件升級、
同步正式機的修正）都是驗收項目的主體，照常列表格。
**絕對不要用 grep「工程師可略」來決定摺疊哪些**——那會讓整個 Task 空掉。
摺疊的判準只有一個：這筆 commit 是不是只改了 query string。

**編譯產物**：`css/*.css` 這類編譯產物不佔獨立的工作項目，
但要在對應節加註「請勿直接修改，一律改 `scss/`」——這是接手者最常犯的錯。

## 用在舊站整體版更時：骨架直接用節點清單

跟 `legacy-site-modernization` 搭配時，上面「先向使用者要工作項目清單」這一步是**已經有答案的**——
骨架就是那 11 個節點，順序照節點編號，不照 commit 時間。三件事因此變簡單，一件事變麻煩：

- **Task 名稱**照抄節點名稱（「移除沒用的檔案」「掃出沒引用的 css/js 並刪除」⋯⋯），
  編號沿用節點編號，讓看報告的人跟 skill 的節點清單逐項對得起來。
- **歸類幾乎是機械的**。那支 skill 要求「每個節點各自對應一個 git commit」，
  所以多數節點就是一筆主 commit 加上零到數筆後續補丁。
- **commit 範圍**的起點就是節點 1 那筆（多半是「移除沒用的檔案」之類的訊息），
  用 `<節點 1 的 hash>^..HEAD`。仍然不要用 `master..<分支>`，理由見〈產出流程〉第 1 步。
- **變麻煩的是驗收對照**：客戶或主管手上的驗收清單用的是他們的說法
  （「資安弱掃要過」「網站要能維護」），跟節點名稱對不起來。
  這時在總覽表多加一欄「對應驗收項目」，或在每節開頭寫一句
  「本節對應報價單第 3 項：資安檢測」，不要擅自把節點名稱改寫成客戶的用語——
  那樣工程端就查不到是哪個節點做的了。

### 各節點典型的「工程端須配合」

這張表是起點不是答案，實際要寫什麼看該專案真的改了什麼。⚠️ 欄位照上面的判準
（漏掉會壞掉的標，漏掉只是沒更新的不標）：

| 節點 | 典型的工程端須配合 | ⚠️ |
|---|---|---|
| 1、2 移除死檔、刪除沒引用的 css/js | 部署時一併移除舊目錄 | 不標；但**後端模板還在引用被刪掉的檔案**時要標 |
| 3 挖出共用區（header/footer） | header/footer 改成 include 或 JS 注入，後端模板要跟著改；`<head>` 的內容在後端模板裡，切版稿改不到 | ⚠️ |
| 4 `<a>`／`<span>` 改 `<button>`、`<img>` 加 `loading="lazy"` | 事件綁定的 selector 變了，不改就沒反應 | ⚠️ 這一節就是上面〈外觀正常，功能壞掉〉講的那類，節末要加引言區塊點明 |
| 5 inline JS／CSS 搬出、CSS 轉 SCSS | `css/*.css` 已是編譯產物，請勿直接改，一律改 `scss/` 後重新編譯；後端模板裡的 inline script／style 也要一起搬 | 編譯產物那條不標，後端模板那條標 ⚠️ |
| 6 內部資源改 CDN | 有內容安全政策（CSP）或外連白名單的話要放行 CDN 網域；`integrity` 的 SRI hash 不可自行改字 | 有 CSP／內網限制才標 ⚠️ |
| 7 Bootstrap 升到 5.3.7 | `data-*` 改成 `data-bs-*`，**後端輸出的 HTML 要一起改**；新增的字型或圖示檔要一起部署 | ⚠️（漏傳字型檔會整批圖示消失） |
| 8 移除 jQuery | 後端模板或其他未納入本次範圍的頁面若還有 `$(...)`，jQuery 標籤拿掉後整段會失效 | ⚠️ |
| 9 升級第三方套件 | 套件被換掉時（例如輪播換一套），後端輸出的 markup 與初始化參數要跟著換 | ⚠️ |
| 10 修復弱掃發現項 | 修在伺服器層的項目（安全標頭、目錄列表、TLS）要主機管理者處理，前端改不到 | ⚠️ |
| 11 加上「不支援 IE」提示 | 提示列的 js／css 要部署，改到的檔案版本號要更新以破快取 | 不標（純部署） |

節點 11 與各節點的破快取 commit（只改 query string 的那些）照〈幾個容易處理錯的情況〉摺疊成一行。
判準只有一個：**這筆 commit 是不是只改了 query string**，不是看 commit 訊息有沒有寫「工程師可略」。

### 版更專案特有的一節：畫面沒變要寫進報告

節點 6 之後的硬約束是「畫面樣式不得改變」。報告裡要有一段交代**你怎麼證明它沒變**——
三層驗收（靜態掃描 → 幾何不變量 → 逐屬性與逐像素）各跑了什麼、比對了幾頁、
有沒有必然改變而事前經使用者拍板的例外（例如 BS3 的按鈕漸層、Glyphicons 換圖示庫）。
非工程背景的窗口最想知道的就是這件事，只寫「已確認沒跑版」沒有說服力。

## 交付清單（結尾必備）

前面是按工作項目切的，工程端需要一份按「我要動什麼」切的。四類：

1. **需部署的檔案**——逐一列出。新增檔（vs 修改檔）特別標明，漏傳新增檔的
   後果通常最嚴重。
2. **模板（`<head>`）需改**——切版稿改得到、但正式站在後端模板裡的部分。
3. **需接後端／JS 的項目**——切版稿只做到 demo 的，明講「這是 demo，請換掉」。
4. **全站一致性檢查**——後端輸出的 HTML 要比照套用的規則。

## 產出流程

1. 向使用者取得工作項目清單與範圍（分支／日期區間／tag）。

   **不要用 `master..<分支>` 當範圍**。長壽的切版分支通常帶著整個專案史，
   這樣撈會混進幾年前的無關 commit（實測某專案撈出 170 筆，本次只佔 66 筆）。
   正確做法是找出本批次的**起點 commit**，用 `<起點>^..HEAD`；
   起點抓不準時先用 `--since='<日期>'` 看日界在哪，再跟使用者確認。

2. `git log --no-merges --format='%h %ad %s' --date=short <範圍>` 全撈。

   兩個讀 log 的陷阱：
   - git log 預設是**拓撲序不是時間序**，合併過的分支會出現日期倒插
     （7/27 的三筆排在 8/10 之後）。別照列表順序推論先後。
   - **commit 訊息不足以判斷歸屬**。一筆「header/footer 改原生載入，
     jQuery 與 Bootstrap 改 CDN」實際同時完成了「inline JS 抽離」與
     「CDN 加 SRI」兩個 Task，光看訊息只看得出前者。
     凡是訊息含糊或動到多處的，用 `git show --stat <hash>` 看實際改了什麼。

3. 逐筆歸類，同時記錄工程端配合事項。
4. **核對筆數**：已列出的 commit 數（含版號摺疊那行）要等於總數。
5. 彙整交付清單。
6. 輸出。預設輸出到與來源同一處（多為 Notion 專案頁下的子頁）；
   使用者沒指定時先問要貼到哪裡：ClickUp 任務／文件、Notion 頁、Markdown 檔，
   還是 Artifact 網頁。貼進看板類工具前先讀下面〈貼進 ClickUp 或其他看板工具〉。

### 貼進 ClickUp 或其他看板工具

**Markdown 檔是正本，先存下來再貼。** 這份文件整份是表格驅動的（總覽表加上每節三欄），
而各家工具對「貼上 Markdown 表格」的處理不一樣，貼壞了要從正本重來，不要只留貼進去那一份。

**先貼總覽表試一次，確認它真的變成表格再貼其餘部分。**（本文件未實測 ClickUp 的轉換行為，
所以寫成「先試再貼」而不是斷言它可以或不行。）沒有正確轉成表格時，改用扁平寫法，
資訊一個都不能少——欄位改成標籤式條列：

```
### 4. 全站按鈕語意改 <button>
狀態：✅ 完成
Commit：`a1b2c3d`、`e4f5g6h`
內容：17 頁共 168 處，各頁前 3 張圖保留不加 lazy 以免影響 LCP
⚠️ 工程端須配合：事件綁定的 selector 從 a.btn-apply 改成 button.btn-apply，不改就沒反應
```

另外兩件事：

- **⚠️ 用文字符號，不要只靠顏色或底色標示**。看板工具的樣式在匯出、通知信、
  手機版裡常常掉光，符號留得住，顏色留不住。
- **短 hash 用反引號包起來**。有些工具會把純數字英數字串吃成連結或自動格式化。
- 如果對方要的是**可勾選的驗收清單**，總覽表可以另外複製一份成工具原生的 checklist
  （一個節點一項），但表格那份仍要保留——checklist 放不下「工程端須配合」那一欄。

## 語氣

讀者是非工程背景的窗口與不熟這份切版稿的工程師。

- 專有名詞第一次出現時附上白話（「`data-parent` 最易漏，漏掉不影響外觀但
  手風琴會失去互斥收起」）。
- 不寫「優化了架構」這種無法驗收的描述，寫得出數字就寫數字。
- 風險講清楚後果，不只講現象：「漏傳會導致圖示全部消失」勝過「請注意字型檔」。
